## 0. The bug, in the engine's own terms

`src/sim/update.rs`'s `update_liquid` (lines 178–197) is three mechanisms tried in order:

```rust
fn update_liquid<S: CellSurface>(surface: &mut S, x: i32, y: i32, rightward: bool) -> bool {
    if try_move(surface, x, y, x, y + 1) {
        return true;
    }
    let (first, second) = if surface.rng().flip() { (-1, 1) } else { (1, -1) };
    if try_move(surface, x, y, x + first, y + 1) || try_move(surface, x, y, x + second, y + 1) {
        return true;
    }
    if transfer_liquid_vertical(surface, x, y) {
        return true;
    }
    transfer_liquid_horizontal(surface, x, y, first, rightward) || transfer_liquid_horizontal(surface, x, y, second, rightward)
}
```

The first two lines — fall straight down, then fall diagonally into open space — are **exactly** `update_powder`'s own first two lines (lines 122–129), reused verbatim as the same `try_move` calls with the same arguments. The module doc names this explicitly: liquid "falls freely like a powder while there's open space to fall into" (line 175). A grain of sand and a droplet of water take the *identical* first movement decision, and a powder pile's defining property — it stops moving the instant every surface cell has diagonal support on both sides, which is the mechanical definition of angle of repose — applies to water during this phase for exactly the same reason it applies to sand. Only once diagonal falling is exhausted does the liquid-specific mechanism start: `transfer_liquid_vertical` (settle onto more of the same liquid below) and then `transfer_liquid_horizontal`, which compares fill against the emptiest reachable cell within `HORIZONTAL_TRANSFER_REACH` (8 cells, `material.rs` line 56) and moves at most half the difference per tick, deliberately capped that way to avoid overshoot-and-oscillate (`update.rs` lines 253–272 explain the halving; `MIN_LIQUID_TRANSFER` at line 242 explains the floor that bounds worst-case settling to under ~1000 frames for a 100-cell pool).

The mitigation already tried was raising `flow_rate` (the per-tick cap on how much fill `transfer_liquid_horizontal`/`transfer_liquid_vertical` may move) from 200 to 1000 — see `assets/materials/water.ron`'s own comment, which documents this exact investigation and its outcome: *"Removing flow_rate as a second, redundant bottleneck lets the halving rule alone govern convergence speed."* It didn't fix the initial-shape problem, because `flow_rate` only throttles the horizontal-transfer mechanism, and the horizontal-transfer mechanism was never what produced the pile shape in the first place — the diagonal free-fall step was, and that step doesn't consult `flow_rate` at all.

So the diagnosis, already correct before this report started: **the bug is not a rate problem, it's a mechanism-ordering problem.** The rest of this report checks that diagnosis against the literature and the practice of comparable engines, and turns it into a concrete recommendation.

## 1. What real particle-based fluid simulation actually is

### 1.1 Where SPH comes from, and what it isn't for

Smoothed Particle Hydrodynamics originates in astrophysics, not graphics: **Gingold, R. A. and Monaghan, J. J. (1977), "Smoothed particle hydrodynamics: theory and application to non-spherical stars," *Monthly Notices of the Royal Astronomical Society* 181(3): 375–389**, [doi:10.1093/mnras/181.3.375](https://doi.org/10.1093/mnras/181.3.375), independently co-invented the same year by **Lucy, L. B. (1977), "A numerical approach to the testing of the fission hypothesis," *The Astronomical Journal* 82: 1013–1024**. Both were solving a mesh-free way to model gas dynamics around stars — nothing to do with real-time graphics, games, or 2D grids. **This paper was not accessible to read directly** (Oxford Academic's MNRAS archive is paywalled at that DOI); everything above is drawn from its abstract/citation record and from every later paper in this section citing it identically. Flagged in §6.

### 1.2 The paper every real-time-graphics SPH implementation cites: Müller, Charypar & Gross 2003

**Müller, M., Charypar, D. and Gross, M. (2003), "Particle-Based Fluid Simulation for Interactive Applications," *Eurographics/SIGGRAPH Symposium on Computer Animation 2003*, pp. 154–159** — read in full from the author's own hosted PDF, [matthias-research.github.io/pages/publications/sca03.pdf](https://matthias-research.github.io/pages/publications/sca03.pdf).

This is the paper that took SPH from an astrophysics tool to a real-time-graphics one. Its actual contributions, precisely:

- **Three purpose-built smoothing kernels**, not one general-purpose kernel reused for everything — the paper is explicit that kernel choice is not incidental. `Wpoly6` (Eq. 20) is used for density estimation because it avoids a square root (`r` only appears squared), but the paper found it unusable for pressure directly: *"if this kernel is used for the computation of the pressure forces, particles tend to build clusters under high pressure. As particles get very close to each other, the repulsion force vanishes because the gradient of the kernel approaches zero at the center."* So pressure uses a separate `Wspiky` kernel (Eq. 21) with a non-vanishing gradient near the center specifically to generate repulsion, borrowed from Desbrun's earlier deformable-body SPH work. Viscosity gets a third, `Wviscosity` (Eq. 22), custom-derived so its Laplacian is positive everywhere — the paper found that reusing a standard kernel for viscosity could make close particles' relative velocity *increase* rather than damp, a real instability in coarse, low-particle-count real-time settings specifically (their words: *"The artifact appears in coarsely sampled velocity fields. In real-time applications where the number of particles is relatively low, this effect can cause stability problems."*).
- **A symmetrized pressure force**, because the naive SPH gradient rule is *not* symmetric between two interacting particles (the pressure force one particle exerts on another isn't automatically equal and opposite) — solved with the arithmetic mean of the two particles' pressures, `f_i = -Σ m_j (p_i+p_j)/(2ρ_j) ∇W(r_i-r_j,h)` (Eq. 10), which the paper states plainly is "a very simple solution which we found to be best suited for our purposes of speed and stability," not the most physically rigorous option available.
- **Real, stated performance numbers** — the paper's own results, not a paraphrase: a 2200-particle glass-of-water scene ran at **20 frames per second** rendering individual particles or a point-splatted surface, on **a 1.8 GHz Pentium IV with a GeForce 4** (2003-era consumer hardware); the same scene with a marching-cubes surface (the visually convincing rendering mode) dropped to **5 frames per second**; a 1300-particle splash scene ran at 25fps; the abstract's own stated ceiling is **"interactive systems... with models consisting of up to 5000 particles."**

That ceiling matters concretely for this engine: 5000 particles was the entire budget for a dedicated, single-purpose fluid demo doing nothing else on 2003 hardware. This engine's playable area is 512×320 = 163,840 cells (`app.rs`'s own `WIDTH`/`HEIGHT` constants, lines 20-21), running sand, water, oil, gas, fire, plant, and structural-integrity logic on the *same* frame budget — not a comparable regime, elaborated in §5.

### 1.3 The problem PBF exists to fix: basic SPH's incompressibility is soft, and it bounces

Robert Bridson's course notes — **Bridson, R., *Fluid Simulation for Computer Animation* course notes** (SIGGRAPH course material; read in full via [cs.ubc.ca/~rbridson/fluidsimulation/fluids_notes.pdf](https://www.cs.ubc.ca/~rbridson/fluidsimulation/fluids_notes.pdf)) — state the honest limitation of Müller et al.'s approach directly, in its own §9.3.1: *"incompressibility is not enforced strictly as in the Eulerian case. Pressure forces are only generated after the fact, when density variations have already formed. This is clearly a penalty method and yields a bouncy behavior of the fluid."* Basic SPH computes density from where particles currently are, derives pressure from *that*, and only then pushes particles apart — density has to visibly deviate from rest density before any corrective force exists at all, which is a lagging, springy control loop, not a hard incompressibility constraint. Fixing this by using a stiffer equation of state just forces smaller time steps to stay stable — a real cost, not a free knob.

### 1.4 Position Based Fluids — Macklin & Müller 2013, and why it needs a GPU to be fast

**Macklin, M. and Müller, M. (2013), "Position Based Fluids," *ACM Transactions on Graphics* 32(4)** — read in full from the author's own hosted preprint, [mmacklin.com/pbf_sig_preprint.pdf](https://mmacklin.com/pbf_sig_preprint.pdf).

PBF is the direct answer to §1.3's problem. Instead of computing forces from a soft equation of state, it poses incompressibility as **one non-linear positional constraint per particle** (`C_i = ρ_i/ρ_0 - 1 = 0`, Eq. 1) solved with Gauss-Seidel-style Jacobi iteration inside the Position Based Dynamics framework (Müller et al. 2007), directly moving particle *positions* to satisfy the constraint rather than integrating forces over a small time step. The paper's own framing of the payoff: *"our method allows similar incompressibility and convergence to modern smoothed particle hydrodynamic (SPH) solvers, but inherits the stability of the geometric, position based dynamics method, allowing large time steps suitable for real-time applications."* Concretely, their own comparison: a competing method (PCISPH) needed 10 sub-steps per frame (Δt = 0.0016s) to stay stable on a bunny-drop scene; PBF was stable with a single full-size step (Δt = 0.016s) on the same scene.

The performance numbers, from the paper's own Table 1 — and this is the number that matters most for this engine's constraints: **128,000 particles at 4.2ms/step, on an NVIDIA GTX 680, implemented in CUDA.** The paper states outright: *"Each stage of our algorithm is fully parallelizable so we are able to take advantage of parallel architectures such as GPUs."* This is not an aside — PBF's entire performance case is a GPU-resident, massively-parallel constraint solve. There is no CPU number in the paper at any particle count, because that was never the target.

### 1.5 PIC/FLIP — invented for plasma physics, brought to graphics for water, adapted for sand

**Brackbill, J. U. and Ruppel, H. M. (1986), "FLIP: A Method for Adaptively Zoned, Particle-in-Cell Calculations of Fluid Flows in Two Dimensions," *Journal of Computational Physics* 65: 314–338** is FLIP's actual origin — a 1986 plasma-physics paper, cited here **secondhand only** (via its citation in both Bridson's notes and Zhu & Bridson 2005 below); no freely accessible copy of the 1986 paper itself was found. Flagged in §6.

The graphics-relevant application is **Zhu, Y. and Bridson, R. (2005), "Animating Sand as a Fluid," *ACM SIGGRAPH 2005*** — read in full via [cs.ubc.ca/~rbridson/docs/zhu-siggraph05-sandfluid.pdf](https://www.cs.ubc.ca/~rbridson/docs/zhu-siggraph05-sandfluid.pdf). This paper is worth engaging with on its own terms, not just as a citation, because **it is close to the mirror image of this engine's actual bug.** Zhu & Bridson start from a working *water* PIC/FLIP solver and add just enough to make *sand* behave like sand — the exact reverse of a water solver that currently behaves like sand.

Their mechanism: every grid cell's stress state is checked each step against the **Mohr–Coulomb yield condition**, `3τ < sinφ·σ_m` (their Eq. 1, τ = shear stress, σ_m = mean/pressure stress, φ = friction angle — literally the same friction-angle concept `material.rs`'s `friction_angle` already encodes for this engine's powders). If a cell satisfies the inequality (shear can't overcome the friction the pressure creates), it is marked **rigid** for that step and its velocity field is projected onto the space of rigid-body motions (one translation + one rotation for the whole connected group). If it fails the inequality, it's marked **flowing**, and updated with a frictional-stress term (their Eq. 2) instead — genuinely incompressible shearing flow, computed with the same pressure-projection machinery an ordinary PIC/FLIP water solver already has. The paper's own framing: *"our domain can be decomposed into regions which are rigidly moving... and the rest where we have an incompressible shearing flow."* Every step, every cell is explicitly classified as one or the other — there is no code path that is *only* ever the rigid-pile rule, the way this engine's `update_liquid` currently *only* ever runs the powder-identical diagonal-fall rule first, unconditionally, regardless of whether the liquid should be behaving as a settled pile or a flowing surface at that moment.

That framing — an explicit, per-region **decision** between "behaving as a rigid/settled mass" and "behaving as a flowing fluid," rather than one hardwired first-mechanism that happens to only ever express the rigid case — is the single most transferable idea from the particle-fluid literature to this engine's CA model, independent of whether PIC/FLIP itself is adopted. §4 returns to this.

On mechanics: PIC/FLIP alternates between a particle representation (for advection — moving material through space without the smearing a pure grid method causes) and a grid (for solving pressure/incompressibility, which is cheap and stable on a regular grid but expensive to do meaningfully with unstructured particles). Plain PIC (Harlow 1963) transfers grid velocity to particles every step, which is numerically diffusive — Brackbill & Ruppel's fix was to instead transfer the *change* in grid velocity, preserving detail PIC would otherwise smear away (Bridson's notes, Zhu & Bridson's own description: *"an almost total absence of numerical dissipation."*). Zhu & Bridson explicitly note the trade FLIP makes is genre-dependent: *"For viscous flows, such as sand, the additional numerical viscosity of PIC is beneficial; for inviscid flows, such as water, FLIP is preferable."*

**Performance, and this is decisive for this engine's constraints: their own headline result — 269,322 particles on a 100³ grid — took approximately 6 seconds per frame on a 2 GHz PowerPC G5 workstation**, described as offline rendering (the paper explicitly discusses `pbrt` rendering afterward, not an interactive viewport). This is a 3D, offline technique. Even granting 2D would be cheaper (roughly the square root of the 3D cost, not linear) and 2026 CPUs are meaningfully faster than a 2005 G5, "seconds per frame, offline, 3D" is not a small gap to close down to "a fraction of a 16.7ms budget, shared with five other simulated materials, 2D, CPU only."

### 1.6 Full Eulerian (grid-based) solvers: why this middle tier doesn't fit either

Bridson's notes are also the right source for the category this report was asked to explicitly rule in or out: a full grid-based Navier–Stokes solver, distinct from both SPH-family particle methods and this engine's existing cell-transfer CA. The core cost driver, from the notes' own §4.3.2 on solving the pressure equation: incompressibility requires solving a global **sparse linear system** every step (the discrete pressure Poisson equation) via Preconditioned Conjugate Gradient — and *"the problem with CG... is that the larger the grid, the longer it takes to converge. It can be shown that the number of iterations it takes to converge to some desired accuracy is proportional to the width of the grid."* That is a fundamentally different computational shape from this engine's CA sweep: every one of this engine's existing update rules (`update_powder`, `update_liquid`, `update_gas`, `fire::update`) is a **local, per-cell decision reading a small fixed neighbourhood**, which is exactly why `parallel.rs`'s rayon checkerboard scheme works at all — its entire correctness proof (`parallel.rs` lines 13–46) rests on every write landing within a bounded reach (`MAX_REACH = 32`, half a chunk) so two chunks in the same pass can never write the same cell. A global pressure solve has no such locality: by construction, one cell's pressure can depend on the whole connected fluid body's boundary conditions, which is exactly why it needs an iterative solver reaching across the whole domain rather than a bounded local update. Retrofitting that into this engine's chunk-parallel architecture would mean either a second, structurally different concurrency model living alongside the CA sweep, or giving up the local-write proof `parallel.rs` currently leans on entirely.

Bridson's own real-time chapter (§7.1) reaches the same conclusion independently, listing the field's own answer for real-time water as **one of three simplified methods — procedural (animate the *look* of water without simulating a cause), heightfield/2D-wave-equation approximations for large open bodies, or small-scale particle systems** — and states outright: *"The constraints described above point out the fact that solving the full 3-d Navier-Stokes equations is still not a practical way of simulating water in games."* None of those three real-time answers is "run the general 3D grid solver, just at a smaller scale" — the actual real-time-games answer from the field's own reference text is to change the *representation* to something structurally cheaper for the specific case, not to run a scaled-down version of the general-purpose solver. That is precisely what §2's falling-sand engines all independently arrived at too.

## 2. How falling-sand engines with liquids actually handle it in practice

The premise going in was that a full particle solver is very likely the wrong tier for a 2D CA engine. Checking that against the genre confirms it more strongly than expected: **no falling-sand engine surveyed uses SPH, PBF, or PIC/FLIP for its bulk liquid.** Every one uses some variety of per-cell CA rule. The genuine variation is in *how* each one avoids this engine's specific bug — a liquid that takes an initial sand-pile shape before slowly correcting.

### 2.1 This engine's own technique is already the standard falling-sand answer — with a citation discrepancy worth fixing

`update.rs`'s module doc already cites the right family of source for the compressible-fill technique: **Tom Forsyth, "Cellular Automata for Physical Modelling,"** [tomforsyth1000.github.io/papers/cellular_automata_for_physical_modelling.html](https://tomforsyth1000.github.io/papers/cellular_automata_for_physical_modelling.html), and a w-shadow.com tutorial. Forsyth's paper describes precisely the mechanism this engine implements: *"In a static body of water whose cells can normally contain one litre of water each, the cells at the top will contain one litre, the ones under them will contain 1.01 litres, the cells under those will contain 1.02 litres, and so on to the bottom"* — a small (~1%), imperceptible overfill that carries a real pressure signal downward, letting a buried cell have a genuinely different fill from its neighbour to equalize against. This is exactly `material::LIQUID_MAX_COMPRESS` (10, i.e. 1% of `LIQUID_FULL`).

**One citation-accuracy note worth fixing, found while verifying this section:** `update.rs`'s doc comment (line 29) links the w-shadow.com post dated **2009-09-29**, "How To Make a 'Falling Sand' Style Water Simulation." Read directly, that specific post does *not* contain the compressible-mass technique — it presents a basic single-occupancy falling-sand algorithm and explicitly defers the liquid-leveling problem to a "Possible Improvements" section (*"Consider adding a simple pressure model"*, stated as unimplemented future work). The post that actually implements the `MaxMass`/`MaxCompress`/`MinMass` compressible-fill technique — the real ancestor of this engine's `LIQUID_FULL`/`LIQUID_MAX_COMPRESS`/`MIN_LIQUID_TRANSFER` — is the **companion post from four weeks earlier**, **2009-09-01, "Simple Fluid Simulation With Cellular Automata,"** [w-shadow.com/blog/2009/09/01/simple-fluid-simulation/](https://w-shadow.com/blog/2009/09/01/simple-fluid-simulation/). Not a correctness bug — the *technique* the code implements is right regardless of which of the two sibling posts gets linked — but worth a one-line fix to `update.rs`'s doc comment so the link actually points at the post containing the mechanism it's cited for.

### 2.2 The Powder Toy: no pressure at all, and a same-step wide search instead

The Powder Toy is open-source (GitHub: [The-Powder-Toy/The-Powder-Toy](https://github.com/The-Powder-Toy/The-Powder-Toy)), and its own community discussion is unusually candid about the limits of its liquid model. From the forum thread on water pressure ([powdertoy.co.uk/Discussions/Thread/View.html?Thread=19810](https://powdertoy.co.uk/Discussions/Thread/View.html?Thread=19810)): *"pressure in liquids and forces between particles are not simulated... weight is only used to determine which particles can be displaced by which other ones"* and, describing the equalization pass that does exist, *"water equalization has a lot of bugs and is very slow."* This is a direct, developer/community-sourced admission that TPT's liquid leveling is not a solved problem in that engine either — useful context for calibrating how hard this problem generally is, not just how well this engine currently does at it.

Mechanically (from `Simulation.cpp`'s `MovementPhase`, fetched and paraphrased — see §6 for the verification caveat): TPT liquids carry a `FLAG_STAGNANT` flag, cleared whenever a particle actually moves. Movement itself searches directly for open horizontal space — up to **`rt = 30` cells when active, or 10 when stagnant** — as part of the *same* movement decision that also handles falling, not as a slower secondary pass bolted on afterward. The practical consequence: TPT's liquids reach a much flatter *initial* shape almost immediately after being placed, purely because the wide-reach horizontal search participates in the very first movement decision, even though TPT has **no compression or pressure concept at all** — a strictly less physically-grounded model than what this engine already has, that nonetheless avoids this engine's specific bug, for a reason directly relevant to §3: it never lets a "look only straight down or diagonally, like a powder" rule run *alone*, unconditioned by anything wider, as the very first thing that happens to a freshly-placed liquid cell.

### 2.3 Sandspiel: CA water, and a separate GPU layer that is easy to conflate with it

Max Bittker's Sandspiel ([maxbittker.com/making-sandspiel](https://maxbittker.com/making-sandspiel/), source: [github.com/MaxBittker/sandspiel](https://github.com/MaxBittker/sandspiel)) is worth a specific correction here because an initial pass at researching it produces a misleading answer. The blog post describes, accurately, a GPU-resident Navier–Stokes solver — *"largely ripped from Pavel Dobryakov's WebGL Navier-Stokes implementation"* — bridged to the CPU-side particle grid via WebAssembly↔WebGL data transfer. It would be easy to read that as "Sandspiel's water is a real fluid solver," but reading the actual `Species::Water` update function in `crate/src/species.rs` shows this is wrong: **`update_water` is an ordinary discrete CA rule** — fall down or diagonally into `Empty`/`Oil`, otherwise a lateral scoot governed by a single per-cell `ra` field (its parity — even or odd — biases which way water leans when spreading sideways, and adjacent water cells compare `ra` parity to propagate that directional lean), no shared liquid-movement helper, no pressure or fill concept at all. (`rb`, initially misattributed to this same mechanism, is unrelated — Sandspiel's other species use it for their own per-species state — burn timers for wood/plant/fungus, a germination countdown for seeds, payload/clone-target species for rocket/cloner — but `update_water` itself never touches it.) The GPU Navier–Stokes solver the blog post describes is a **separate system entirely — wind/advection, used for particle drift and visual flourish, not for how water finds its level.** This matters for the report's own honesty standard: even a small early WebFetch summary of the same source material conflated the two, which is exactly the kind of secondary-source risk this report is trying to avoid passing on to the codebase's own documentation.

### 2.4 Noita: confirmed publicly, and the honest limit of what's confirmed

Nolla Games has spoken publicly about "Falling Everything" primarily through one GDC talk — **Purho, P., "Exploring the Tech and Design of Noita," GDC 2019**, session page: [gdcvault.com/play/1025695](https://www.gdcvault.com/play/1025695/Exploring-the-Tech-and-Design), publicly mirrored on YouTube. What's independently corroborated across secondary sources (an [80.lv technical writeup](https://80.lv/articles/noita-a-game-based-on-falling-sand-simulation) and the game's own [Wikipedia entry](https://en.wikipedia.org/wiki/Noita_(video_game))) as a paraphrase of that talk:

- Liquid movement is a discrete per-pixel rule: *"Liquid pixels first check if they can go down. If not, they check left and right to see if they can move that way,"* with density comparisons used to decide displacement (a denser liquid sinks through a lighter one) — structurally the same category of rule as this engine's `try_move` density-displacement check, not a diffusion or pressure model.
- The world is chunked at **64×64** (identical to this engine's own `CHUNK_SIZE`, coincidentally or not) with per-chunk dirty rectangles, the same optimization this engine's own chunk system already implements.
- Debris and splashes are handled by an **off-grid particle system layered on top of the CA grid** — this engine's own `particle.rs` module doc says outright, *"Noita does the same split for the same reason"* (line 13), already citing this precedent for exactly the design this engine independently arrived at. See §4.
- Fire/water/oil interactions (fire stops at water, converts water to steam on contact) are confirmed in both sources.

**What is not publicly confirmed, and should not be presented as fact:** a more elaborate description — that Noita computes per-cell "influx/efflux" between neighbours through a ping-pong buffer with a 50%-of-difference-per-frame cap (which, if true, would be strikingly close to this engine's own halved-transfer rule) — surfaces in web search results attributed to a blog post, **Shamus Young, "Noita: Sim Misfortune,"** [shamusyoung.com/twentysidedtale/?p=50036](https://www.shamusyoung.com/twentysidedtale/?p=50036). Reading that post directly, the author states plainly, *"I have no idea how the developers accomplished this,"* and the influx/efflux/ping-pong description actually originates in that post's **comment section**, from other readers speculating about how such a system *could* work in general — not a developer statement, not sourced to the GDC talk, and not confirmed anywhere else checked for this report. **This report does not repeat that description as a fact about Noita.** If the owner wants Noita's actual liquid-leveling mechanism beyond "check down, then sideways, density-swap," the GDC talk itself (video, not a secondary summary) is the source to go to directly — flagged again in §6.

### 2.5 A heavier-CA data point for contrast: Dwarf Fortress

Worth including as the other end of the CA-liquid spectrum from TPT/Sandspiel/Noita's simple discrete rules: Dwarf Fortress's fluid system, documented on its own wiki ([dwarffortresswiki.org/index.php/DF2014:Fluid_logic](https://dwarffortresswiki.org/index.php/DF2014:Fluid_logic), [.../Pressure](https://dwarffortresswiki.org/index.php/DF2014:Pressure)), quantizes fill into **8 discrete levels (0–7)** rather than a continuous scale, and implements genuine pressure propagation: a fully-full (7/7) tile can trace a connected path of other full tiles — down and horizontally, never diagonally — to push fluid out at a distant point, even *uphill*, as long as the traced path never rises above the source tile's own level. This is a heavier, more "real" pressure model than this engine's compressible-fill approach — and it is also the CA liquid technique with the worst-documented reputation for edge-case bugs and performance cost among the games surveyed here (the mechanism is colloquially known in the DF community for "teleporting" fluid unrealistically along a traced path, and for being one of the more expensive systems in the game to run at scale). Useful calibration: quantized-with-real-pressure-propagation is a real point on the spectrum, but it buys a specific kind of correctness (long-range pressure effects) this engine's `HORIZONTAL_TRANSFER_REACH`-bounded model deliberately doesn't attempt, at a cost and bug-surface trade the genre's own most pressure-faithful implementation is generally regarded as not having fully paid off.

### 2.6 The pattern across all of them

Every falling-sand-genre engine surveyed — this one included, before this investigation — independently converges on the same tier: **a discrete, local, per-cell CA rule for liquid, never SPH/PBF/PIC-FLIP for the bulk fluid.** Where they differ is entirely in *how quickly the CA rule's first movement decision produces something that already reads as liquid* rather than needing a slow secondary process to fix it after the fact:

- TPT: a single wide reach search (`rt` up to 30) is part of the *same* movement step that also handles falling — never a rule that can, by itself alone, only ever express a sand-pile shape.
- Sandspiel: no compression concept at all, but also no separate "fall like powder first" phase distinct from its lateral-scoot logic — the lateral move is checked on the same pass.
- Noita: check-down-then-sideways with density-swap, again as one rule evaluated together, not gated behind an unconditional powder-identical phase first.
- This engine, currently: the *only* one surveyed where the liquid-specific mechanism (the technically correct, Forsyth-style compressible-fill diffusion) is placed strictly **after** an unconditional, powder-identical free-fall phase that has no liquid-awareness at all and therefore reproduces powder's own defining behaviour — stopping at angle of repose — before the liquid-aware mechanism ever gets a turn.

## 3. Diagnosing this engine's bug against that pattern

The playtest-confirmed root cause — the diagonal free-fall step is shared, unmodified, powder movement code, and it alone determines the *initial* shape because it runs to exhaustion before either liquid-specific mechanism gets a turn — is not just correct, it is now explicable in the same terms every other falling-sand engine's design already uses. This engine picked the technically right family of long-run mechanism (Forsyth-style compressible-fill diffusion, §2.1) — genuinely more physically grounded than TPT's no-pressure model or Sandspiel's momentum-hint fields — and then gated it behind a phase that has no concept of liquid at all. Every comparable engine surveyed avoids this specific failure not by having a more sophisticated long-run mechanism, but by making sideways movement participate in the *first* movement decision a cell makes, not a decision deferred to a slower pass reached only once the powder-identical phase has nothing left to do.

Put in Zhu & Bridson's terms (§1.5): this engine currently has no equivalent of their yield-condition check. A liquid cell never asks "am I actually settled/rigid right now, or should I be flowing?" — it always runs the settled-pile rule first, unconditionally, and only afterward (much later, in wall-clock frames) does the flowing-fluid rule get a chance to correct the result. The fix implied by that framing is not "adopt PIC/FLIP" — §1.5 and §1.7's numbers rule that out on cost grounds alone — but the *shape* of the fix generalizes cleanly to a CA rule: give a liquid cell a same-step way to recognize "there's a lower or equal-fill opening within reach sideways" and act on it before or alongside the diagonal-fall check, rather than only after the diagonal-fall check has already produced a powder-shaped rest state for it to slowly erode away from.

## 4. What this engine already has that's directly relevant: `particle.rs`

Worth naming explicitly, because it changes what "just add particles" would actually mean here. This engine already has an off-grid particle system — `src/sim/particle.rs`, built for M15 explosion debris, module doc citing the same Noita precedent as §2.4: *"A CA cell moves at most one cell per frame, by rule, not by an actual velocity... Free particles are a completely separate system for exactly that case — a `Vec<Particle>` with float position and velocity, gravity, and a landing check against the CA grid that converts a particle back into a normal cell the moment it would overlap something solid. Noita does the same split for the same reason"* (lines 4–12).

This is directly relevant to whether "lightweight particle-based liquid" is a shortcut worth taking, and the honest answer is that it isn't, for a specific reason grounded in Bridson's own taxonomy (§9.1 of his notes): `ParticleSystem` is what Bridson's notes call a **"simple particle system"** — *"a particle system without particle-particle interaction... implemented very efficiently... a set of decoupled ordinary differential equations."* `particle.rs`'s own particles carry no interaction force with each other at all (confirmed reading the struct and its module doc: position, velocity, a per-particle drag and gravity-scale drawn once at spawn, plus material/shade for rendering — nothing resembling a neighbour query or an interparticle force). That is fine and correct for what it's built for — ballistic debris that should scatter independently — but it is structurally incapable of producing liquid-leveling behaviour on its own, because leveling requires particles to *feel* each other (Bridson's own §9.2: *"If we want to simulate small bodies of water with particles, it is quite essential that the particles feel each other. Otherwise, they all aggregate at a single spot."*). Adding that — an actual interaction force, i.e. turning `ParticleSystem` into an SPH solver — is not a shortcut around §1's cost analysis; it's re-deriving §1's entire problem from a different starting file. The existing free-particle system is the right tool for what it already does (splash debris, explosion scatter) and is not a latent liquid solver waiting to be switched on.

## 5. Recommendation

**Do not adopt SPH, Position Based Fluids, or PIC/FLIP for this engine's bulk liquid.** This is not a default answer reached without checking the alternative — §1 and §4 are that check, done directly against this engine's own numbers:

- **No GPU compute path exists to run any of them on.** Confirmed directly against `Cargo.toml`: the only relevant dependencies are `pixels` (a software-framebuffer-to-window blit, itself built on `wgpu` — confirmed via `Cargo.lock`, where `wgpu` appears only as `pixels`'s transitive dependency, never a direct one) and `rayon` (CPU thread-pool parallelism, already used for the existing checkerboard CA sweep in `parallel.rs`). `src/main.rs` and `src/render.rs` reference `wgpu` only in comments about the presentation swapchain, never for compute. Position Based Fluids' entire real-world performance case (§1.4) is CUDA-on-GPU; this engine has no compute shader, no CUDA, no `wgpu` compute pipeline wired to anything.
- **The numbers don't fit even generously.** This engine's playable area is 512×320 = 163,840 cells, already running six material kinds' worth of CA rules plus fire/heat/structural/plant systems inside a documented ~16ms worst-frame budget (`fire.rs`/`material.rs`, both citing the same measured "~16ms to ~64ms" full-screen stress figure). Müller et al.'s 2003 real-time SPH paper's own stated ceiling was 5000 particles *for a dedicated single-purpose demo* on hardware from that era; this engine would need a meaningfully larger particle budget than that just to represent one modest pool of water at a comparable visual density to what the grid already shows, while also running everything else already sharing that frame. PBF needs a GPU to hit even 128k particles at a few milliseconds; Zhu & Bridson's PIC/FLIP-for-granular-material technique runs at ~6 seconds a frame, offline, in 3D.
- **The architectural mismatch is real, not just a performance gap.** §1.6 and §4 both land on the same point from different directions: every real particle/grid fluid technique surveyed needs either global coupling (an Eulerian pressure solve reaching across the whole connected fluid body) or a genuinely interacting particle set (SPH's neighbour-force computation) — both structurally different from the bounded-local-write model `parallel.rs`'s entire chunk-parallel correctness proof depends on. Retrofitting either would mean a second concurrency model living alongside the CA sweep, not a drop-in replacement for one movement rule.

**The right fix is the one the diagnosis in §3 already points at: fix the CA algorithm's mechanism ordering, not its tier.** Concretely, as a direction (not a finished design — the actual constants and exact search shape are an implementation-time decision, not a research-report one):

- **Give `Liquid` kind a same-step, bounded-width horizontal search for a lower-or-emptier opening, evaluated before or alongside the diagonal-fall check** — not gated behind it the way `transfer_liquid_horizontal` currently is. This is the one property every comparable engine's approach in §2 shares and this engine's current code lacks: sideways movement participating in the very first decision a freshly-placed liquid cell makes, not deferred to a slower pass reached only once the powder-identical phase has already produced a settled, sand-shaped rest state.
- **This does not mean discarding the existing compressible-fill mechanism** (`transfer_liquid_vertical`/`transfer_liquid_horizontal`, `LIQUID_FULL`/`LIQUID_MAX_COMPRESS`/`MIN_LIQUID_TRANSFER`). That mechanism is the technically correct long-run leveling process — Forsyth's own technique, already validated by this engine's own passing tests (`a_wide_deep_water_column_levels_out_instead_of_only_eroding_at_the_edges`, `water_settles_flatter_than_a_powder_would`) — and nothing in §1 or §2 suggests replacing it. The problem this report was asked to solve is specifically the *first few frames*' visible shape, not the eventual-convergence behaviour, which the engine's own tests already show working.
- **The reach for this new same-step search should almost certainly reuse `HORIZONTAL_TRANSFER_REACH`** (already `Material::sweep_reach`'s answer for `Liquid`, already accounted for in the chunk dirty-rectangle widening `chunk.rs` depends on) rather than introducing a second, different reach constant that would need its own `sweep_reach` accounting and its own proof that `parallel.rs`'s cross-chunk write-safety argument still holds. Reusing the existing bound is what keeps this a same-tier algorithmic fix rather than a new performance or correctness surface.
- **This is squarely inside the design-philosophy boundary already settled for this codebase** (`design-philosophy.md` §2b): it's a mechanism change ("liquid gets to look sideways before it's allowed to look only down-then-diagonal"), not an authored outcome ("water should look like X"). The shape that results is a side effect of when the existing rules get to run, exactly the kind of change that document says is always fine.

**What this report is explicitly not doing:** proposing the exact new function signature, the precise interaction between a new same-step search and the existing `transfer_liquid_horizontal`, or the specific constant to reuse or introduce. That is implementation work with its own test-driven verification loop (the engine already has `water_settles_flatter_than_a_powder_would` and the 100-cell-wide column test as a scaffold to extend), not a conclusion a research pass should reach on its own.
